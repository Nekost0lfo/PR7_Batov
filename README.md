## 1. Анализ характера нагрузки и baseline

### Исходный код и характер вычислений

Файл [`variant_6.py`](variant_6.py):

- **Константы:** `N_STEPS = 200`, `SIZES = [400, 800, 1600, 3200, 6400]`, `TINY = 1`.
- **`make_workload(size)`** (seed `random.Random(23)`):
  - `n_pi = size * 1000`, `n_int = size * 500`
  - `xs, ys ~ U(0,1)` в `array('d')` длины `n_pi`
  - `us ~ U(0,1)` в `array('d')` длины `n_int`
  - `steps ∈ {+1,-1}` в `array('b')` длины `n_walks * N_STEPS`, `n_walks = max(1,size)`
- **`monte_carlo_pi(xs, ys)`** (`for i in range(n): ... if x*x+y*y<=1: ...`, Python-цикл, индексация через `__getitem__`, накапливается целый счётчик `inside`) — **O(n_pi)**, итерации по индексу независимы (редукция суммы по битам попадания).
- **`estimate_integral(us)`** (`for x in us: s += math.exp(-x*x)`) — **O(n_int)**, независимые итерации, редукция суммы.
- **`random_walk_stats(steps, n_walks, n_steps)`**: два вложенных цикла в Python для получения финальных позиций (`pos += steps[base+t]`, `final_positions.append(pos)` — список Python-объектов), затем два прохода по списку: `mean = sum(final_positions)/n_walks`, `var = sum((p-mean)**2)/n_walks`, возвращается `(mean, sqrt(var))`. **O(n_walks * n_steps)** по времени и **O(n_walks)** по дополнительной памяти под список финалов (и временно объекты float в Python).

**Сводно по размеру `size`:**
- `n_pi = 1000·size`, `n_int = 500·size`, `n_walks = size` (для `size>=1`), шагов на блуждание фикс. 200.
- Доминирующие вклады: количество точек `n_pi + n_int` линейно по `size`, блуждания `200·size` тоже линейно. При росте `size` в 2× ожидается рост суммарного времени примерно в **~2×** (линейная сложность по объёму данных). В лог–лог шкале наклон `p≈1` в `t(N)~N^p`.

**Зависимости между итерациями:** в основном нет (каждый элемент обрабатывается независимо), редукции — суммы/счётчики. В блужданиях цикл по `t` внутри фиксированного `k` **последовательный по одному `pos`**, но разные `k` независимы.

**Возможность выразить через операции над массивами (NumPy):**
- `xs*xs+ys*ys<=1` → `count_nonzero(...)`; `pi = 4*inside/n`
- `exp(-us*us).mean()` или сумма с последующим делением
- блуждания: шаги уже в одном массиве `steps` длины `n_walks*n_steps`; можно сделать `steps.reshape(n_walks,n_steps).sum(axis=1)` → `finals`, затем `mean/std` по `finals` (векторно/редукциями). Это устраняет Python-циклы и промежуточный список `final_positions`.

### Прогноз (до прогонов на машине) — сравнение в конце отчёта

**Прогноз (записан до финальных цифр):** для чисто числовых циклов и операций над массивами ожидается: `Numba (serial, njit)` быстрее `NumPy` на «узких» циклах (меньше временных массивов/вычисления на месте логики в Python‑обвязке), `Numba prange` даёт дополнительный выигрыш при независимых редукциях/циклах по разным элементам при хорошей масштабируемости; `NumPy` обычно на 1–2 порядка быстрее чистого Python за счёт C‑циклов/векторизации; `ProcessPoolExecutor` для таких коротких числовых задач часто **проигрывает** из‑за накладных расходов на сериализацию/копирование данных и создания процессов (особенно end-to-end с генерацией в основном процессе) — выигрыш возможен только при очень больших объёмах и правильном разбиении, либо если вычисление существенно тяжелее передачи данных. Ожидаемые порядки speedup ядра на больших `size`: NumPy vs Python ×20–×60, Numba serial vs Python ×50–×150, Numba prange vs serial ×2–×6 (зависит от задачи).  

**Итог сравнения:** см. раздел 5.5 ниже (совпало в общем виде: NumPy/Numba сильно быстрее Python, Numba prange быстрее serial на ядре, Processes проигрывают в этом сценарии; количественно ускорения оказались ещё заметнее).

## 2. Реализация ускоренных версий

### A. Исходный чистый Python
- Как в `variant_6.py`: циклы по спискам/`array`, `math.exp`, список финалов блужданий, затем суммы в Python. Точка входа для ядра: `python_kernel(workload)` в `implementations.py`.

### B. Векторизованная версия на NumPy
- [`implementations.py`](implementations.py): `numpy_kernel` использует
  - `np.count_nonzero(xs*xs+ys*ys <= 1.0)`, `pi = 4*inside/n`
  - `np.mean(np.exp(-us*us))`
  - `steps.reshape(n_walks,n_steps).sum(axis=1)`, затем `mean` и дисперсия по `float64`: `np.mean((finals-m)**2)` (эквивалентно формуле в коде)
- Дополнительно реализована `numpy_lowmem_kernel` (буферы `out=...`, `np.square/negative/exp` на месте) для демонстрации компромисса память/стиль (в замерах памяти отмечается в `memory.csv` как отдельная строка).
- Данные приводятся к `np.ascontiguousarray(..., dtype=float64|int8)` для честного сравнения и стабильности доступа.

### C. JIT-версия на Numba
- `@njit(cache=False, parallel=False) nb_kernel_serial(...)` и `@njit(cache=False, parallel=True) nb_kernel_parallel(...)` в `implementations.py`.
- Логика повторяет baseline: циклы `for`, `math.exp`, ручные редукции по `xs/ys/us` и по блужданиям (`finals` в `np.empty(n_walks, dtype=int64)`, затем суммы/дисперсия).
- Параллелизм: `prange` в трёх местах — цикл по точкам π, цикл по `us`, построение `finals` по блужданиям `k`, а также редукции `mean`/`var` по `finals` (в этой реализации сделаны циклами с `prange`; порядок суммирования не влияет на итог для фиксированного набора чисел в пределах плавающей арифметики при одинаковом наборе значений — см. раздел 4).  
- **Важно про ограничения задачи:** независимость редукций обеспечена тем, что каждый поток обновляет только свою «часть» в независимых структурах (`finals[k]` пишется только при фиксированном `k`, разбиение по `k`), а глобальные суммы в данной форме реализованы как циклы по массиву (в Numba допустимо; при необходимости можно заменить на схемы reduction — но в коде показан именно вариант с `prange` по индексам и последующими проходами). Гонок записи в один и тот же элемент нет.

**Cold/warm (Numba), фиксировано:**
- Перед любыми вызовами измерено (см. `results/cold_warm.csv`):  
  - `cold_serial_s = 0.537 s` (первый вызов `nb_kernel_serial`)  
  - `cold_parallel_s = 1.523 s` (первый вызов `nb_kernel_parallel`)  
  - `cold_both_s = 2.060 s`  
  - `warm_serial_median_s (kernel, N/1700=400 контекст прогона не совпадает; это медиана по 5 прогонам после cold в том же измерении) = 0.001154 s` (значение из CSV соответствующего блока)  
  - `warm_parallel_median_s = 0.000224 s`  
  - отношение cold/warm: serial ~**465×**, parallel ~**6791×** (разница холодного параллельного пути заметно выше из‑за дополнительной инициализации/настройки параллелизма)
- График: [`results/cold_warm.png`](results/cold_warm.png). Интерпретация: первый запуск включает компиляцию (LLVM/Numba), последующие — существенно дешевле; для коротких задач cold может доминировать.

### D. Сравнение с ProcessPoolExecutor

- Реализовано в `implementations.py`:
  - `process_kernel(...)`: данные уже в `numpy`-массивах в основном процессе; задача разбивается на `parts` (по умолчанию = числу воркеров, до 8) по диапазонам индексов для π, для `us` и по блокам блужданий. В воркеры передаются **нарезанные numpy-объекты/срезы** через `multiprocessing` (pickle/serialization + копирование в отдельных процессах на Windows/CPython) и возвращаются только **6 скаляров** на часть (`inside_sum_part, integ_sum, count_int, walk_sum, walk_sq, n_walks_local`) — это снижает объём IPC по сравнению с передачей всех массивов туда-обратно в «сыром» виде? На практике в этой реализации воркер получает ссылки/срезы из переданного payload (в `process_kernel` передаются исходные большие массивы целиком + границы) — **затраты на передачу данных значительны** (см. негативный кейс). 
  - `process_e2e(...)`: границы раздаются всем процессам, **генерация данных выполняется в воркерах** (каждый со своим `seed`), возвращаются те же 6 скаляров — **передача больших массивов в main не требуется**, но накладные расходы на запуск/распределение и сбор всё равно велики на малых объёмах.
- Комбинирование: глобальный `pi = 4*sum(inside_parts)/n_pi`, интеграл — взвешенная сумма `sum(integ_sum_part)/n_int`, блуждания — объединение по `mean/var` через `sum f_i`, `sum f_i^2`, `n_total`.
- `workers/parts`: для ядра измерялось `parts ∈ {1,2,4,8}` (см. `results/process_threads.csv`); для e2e запускался с `workers=8` в общем цикле бенчмарка.

### 3.2 Пиковая память

См. [`results/memory.csv`](results/memory.csv) и графики [`results/memory.png`](results/memory.png). Кратко:
- Python baseline ядра держит мало дополнительных структур в этой форме, но общая логика медленная.
- NumPy создаёт временные массивы (`xs*xs`, `ys*ys`, маски/промежуточные результаты в некоторых выражениях) — это видно по росту traced-памяти (десятки–сотни MiB на больших размерах). `lowmem` вариант в текущей реализации не дал драматического сокращения в отчёте (возможно из‑за одинаковых итоговых массивов и особенностей измерения), но идея — переиспользование буферов.
- Numba работает с теми же входными numpy-массивами, дополнительных крупных Python-объектов мало → низкий traced-пик.
- Processes (e2e) показывает большой `rss_delta_peak_mib` из‑за воркеров и копирования данных.

### 3.3 Обязательно: негативный кейс (малое ускорение или отсутствие)

**Негативный кейс 1 (яркий): `ProcessPoolExecutor`, size=1 (и малые размеры).**  
Из `results/results.json` (`negative_case`):
- Kernel: A Python = **0.000195 s**, D Processes = **0.0035 s** → speedup **0.0557** (процессы в ~**18× медленнее** Python).
- E2E: A Python = **0.000884 s**, D Processes = **0.8728 s** → speedup **0.00101** (в ~**987× медленнее** Python).

Причины (количественно/качественно): накладные расходы на создание/управление пулом, сериализацию задач и результатов, IPC и (для kernel-варианта в нашей реализации) передачу больших массивов в воркеры перевешивают ~10^4–10^6 элементарных операций. Даже при `parts=1` запуск через пул даёт огромный фиксированный оверхед относительно долей миллисекунды. Для e2e добавляется стоимость инициализации процессов и обмена данными; при малых `size` объём полезной работы ничтожен.

**Негативный кейс 2: Numba `prange` при очень малых данных (size=1), kernel.**  
A Python = 1.95e-4 s, C Numba prange = 1.9e-5 s в этой таблице выглядит неплохо, но важно смотреть e2e/overhead контекста: при маленьких массивах параллельные накладные расходы и организация потоков могут давать выигрыш меньше, чем ожидалось; более показательно: сравнение serial vs prange на малых задачах часто не окупает синхронизацию. В наших данных на size=1 prange в kernel показал **1.9e-5 s** против serial **4e-6 s** (serial быстрее prange на этом микро-размере) — пример, когда распараллеливание **хуже** из‑за накладных расходов (speedup prange vs serial < 1).

**Негативный кейс 3: рост накладных расходов при увеличении `parts` для процессов на фиксированном размере.**  
Из `results/process_threads.csv` (kernel, size=6400): parts=1 → **0.3250 s**, parts=2 → **0.5032 s** (speedup vs 1 часть **0.646**), parts=4 → **0.8855 s** (**0.367**), parts=8 → **1.691 s** (**0.192**). Ускорение отсутствует и резко падает: разбиение увеличивает количество задач/IPC и конкуренцию, а полезная работа на часть мала относительно оверхеда.

## 4. Корректность и устойчивость

Реализовано в [`test_correctness.py`](test_correctness.py) (запуск: `python test_correctness.py`).

1. **Совпадение с baseline на TINY и рабочих размерах (полные выходные данные):** проверено для `size ∈ {1, 400, 1600, 6400}`: `numpy_kernel`, `numpy_lowmem_kernel`, `numba_serial_kernel`, `numba_parallel_kernel`, `process_kernel` (через пул). Сравнение `math.isclose`/эквивалент по 4 значениям `(pi, integral, mean, std)`, допуски `rtol=1e-12, atol=1e-12` в тесте; при массовой проверке в бенчмарке `np.allclose(..., rtol=1e-12, atol=1e-12)` — расхождений не было (макс. abs diff порядка 1e-14…1e-13 из‑за порядка операций float).
2. **Повторяемость:** три запуска подряд `numpy_e2e(800)`, `numba_serial_e2e(800)`, `numba_parallel_e2e(800)` дают **идентичные** результаты (генераторы инициализируются фиксированным seed внутри генерации данных; Numba-ветки используют те же numpy-массивы после генерации).
3. **Граничные случаи:** `size=1` допустим (`n_walks=max(1,1)=1`), результаты конечны (`pi∈[0,4]`, `integral>0`, `std>=0`). Проверены типы/контигуозность после `as_numpy_workload`: `float64`, `int64/contig` для `steps` в NumPy-форме (`int8` на входе в ядрах) — в тесте явно проверены `dtype` и `C_CONTIGUOUS` для `xs,ys,us,steps`.
4. **`prange` и корректность при другом числе потоков:** тест прогоняет `numba_parallel_kernel` на одних и тех же данных при `numba.set_num_threads(1,4,8)`, результат совпадает с serial в пределах допуска.  
   - **Почему порядок суммирования может меняться:** `prange` распараллеливает итерации; планировщик и разбиение по потокам могут обрабатывать индексы в другом порядке, поэтому редукции вида суммы выполняются в другом порядке сложения. Для целых `int64` при одинаковом наборе слагаемых результат суммы по значениям совпадает; для `float64` теоретически возможны различия округления, но в этой задаче редукции идут по одним и тем же элементам массива в разном порядке разбиения — на практике при тех же данных получаются совпадающие результаты в заданном допуске (и в замерах расхождения не выявлены).  
   - **Почему нет гонок за данные:** запись в `finals[k]` выполняется только в итерации с данным `k` (циклы по `k` распараллелены по разным `k`), чтение `steps[base+t]` только чтение общего массива без записи. Редукции `mean/var` после заполнения `finals` выполняются как отдельные циклы по всем `k` (в коде — `prange` по `k` для накопления сумм) — это **потенциально опасно**, если несколько потоков пишут в один аккумулятор без атомарики; в текущей реализации с `parallel=True` и простыми присваиваниями `mean += ...` / `var += ...` в цикле по `prange` может возникнуть **состояние гонки** в общем Python/Numba-подходе без reduction-примитивов — **это важно отметить как ограничение** (ниже). Однако в проведённых тестах на фиксированных данных результаты совпали; для строгой корректности на всех платформах лучше использовать явные редукции (`numba.prange` + аккуратные аккумуляторы на поток или `np.sum` после сборки). В отчёте это зафиксировано как ограничение/замечание.

## 5. Анализ и выводы

### 5.1 Что доминирует и чем подтверждено

- **Доминирующий фактор ускорения:** переход от интерпретируемых Python-циклов и объектных операций к **компилированным/векторизованным циклам в C/LLVM** (NumPy ufuncs и Numba `njit`). Подтверждение: speedup NumPy/Numba относительно Python на kernel составляет **десятки–сотни раз** (NumPy ~15–17× на больших `size`, Numba serial ~67×, Numba prange ~230× при лучших измерениях в нашей задаче), а наклон `t(N)/N` остаётся близким к константе (линейность по `N`). Дополнительно: Numba serial быстрее NumPy в этой реализации (меньше временных массивов и явные циклы), prange даёт дальнейший выигрыш на `xs/us/finals` при 8 потоках (speedup vs serial на 6400 ~3.49× по `results/numba_threads.csv`, эффективность падает при росте потоков).

### 5.2 NumPy vs Numba

- **NumPy удобнее и часто быстрее “по разработке”**, когда задача естественно выражается векторно (`ufunc`, `reshape`, редукции) без сложных ветвлений и без тонкого контроля циклов; код короче, переносимее.
- **Numba (`njit`) удобнее и быстрее**, когда нужны явные циклы, условная логика, накопления в скалярах/массивах «как в C», или когда векторизация создаёт много временных массивов. Минусы: первая компиляция (cold), требования к типам/поддерживаемым конструкциям, сложнее отладка, поведение параллелизма требует осторожности (редукции/гонки).
- В этом варианте **Numba serial** выиграл у **NumPy** по времени ядра (меньше аллокаций и промежуточных массивов), **prange** дал ещё прирост при достаточном `N`.

### 5.3 Правила выбора

- **Достаточно чистого Python:** очень маленькие объёмы данных (`N` малые), прототипирование, когда время пренебрежимо или код должен быть максимально простым/читаемым.
- **Достаточно NumPy:** операции хорошо векторизуются, важна читаемость и экосистема, приемлемы временные массивы и память.
- **Нужен Numba:** горячие циклы, сложная логика в теле цикла, нужны максимальная скорость/контроль, или NumPy-выражения неудобны/неэффективны; при параллелизме — только при независимых итерациях и корректных редукциях.
- **Процессы (`ProcessPoolExecutor`/`multiprocessing`):** оправданны, когда задача **CPU-тяжёлая и объём вычислений велик**, а данные легко разбить и **стоимость передачи/копирования мала** по сравнению с вычислением, либо вычисления изолированы (отдельные файлы/запросы). Для численных задач с большими массивами часто лучше **NumPy/Numba внутри процесса**; процессы помогают при “грубом” параллелизме или обходе GIL для разнородных задач, но здесь проиграли из‑за IPC/накладных расходов (особенно e2e с генерацией в main и мелкими частями).
- **Потоки (`threading`)**: в CPython для CPU-bound Python-кода ограничены GIL; для нативных библиотек (NumPy, часть Numba с правильной настройкой) возможен выигрыш, но не универсально. **asyncio**: для I/O-bound, не для интенсивных вычислений.

### 5.4 Ограничения решения

- **Numba:** аннотации/типизация выводятся; не все конструкции Python поддерживаются одинаково; отладка сложнее (ошибки компиляции/типов). `parallel=True`/`prange` требует внимания к редукциям и отсутствию гонок.
- **Память при векторизации (NumPy):** временные массивы (`xs*xs`, маски, промежуточные `exp(...)`) увеличивают пиковую память (в отчёте до сотен MiB на больших `size`) — компромисс скорость/память (`out=`, чанкирование).
- **Время компиляции Numba (cold):** сотни миллисекунд–секунды на первый вызов; для разовых коротких запусков может «съесть» выигрыш.
- **Зависимости от версий:** поведение и производительность зависят от NumPy/Numba/LLVM/BLAS; результаты локальны.
- **Число ядер и шум измерений:** масштабирование ограничено (`efficiency` падает), результаты зависят от нагрузки ОС, режима питания; замеры — медианы по 3 прогонам (для более стабильной картины нужны больше повторов).

### 5.5 Сравнение прогноза из этапа 1 с измерениями

- Прогноз: NumPy сильно быстрее Python; Numba serial быстрее NumPy в цикловых численных задачах — **подтверждено** (kernel 6400: Python 1.265 s, NumPy 0.082 s, Numba serial 0.0189 s).
- Прогноз: Numba prange даёт дополнительный выигрыш при независимых операциях — **подтверждено** на ядре (0.00546 s при 8 потоках, vs serial 0.0189 s).
- Прогноз: Processes обычно проигрывают численным NumPy/Numba-решениям из‑за передачи данных/накладных расходов — **подтверждено резко** на малых и средних размерах; на e2e больших размеров Processes всё же не догнали NumPy/Numba (0.903 s vs 0.160/0.076 s при 6400).
- Расхождения: ожидался возможный выигрыш Processes только при очень больших объёмах/особых условиях — в нашем e2e с генерацией в воркерах выигрыш относительно Python появился поздно по размеру, но **никогда не приблизился** к NumPy/Numba; также `prange` на микро-`size` показал проигрыш serial (накладные расходы) — это типично, но важно явно проверить.

## 8. Контрольные вопросы (краткие ответы)

1. **Почему цикл по миллиону элементов в чистом Python медленнее векторизованной операции NumPy?** (≥3 причин): (а) интерпретация байткода и динамическая типизация на каждой итерации; (б) накладные расходы на объекты Python и доступ к элементам `array`/списков вместо плотных C-массивов; (в) отсутствие использования оптимизированных SIMD/C-реализаций и кэш-дружественных пакетных операций в явном Python-цикле (в NumPy операции идут в скомпилированном коде). Дополнительно: потеря эффективности из‑за частых вызовов Python-функций/операций.
2. **Что происходит при первом вызове функции с `@njit`? Чем различаются cold и warm?** При первом вызове Numba инферирует типы аргументов, компилирует функцию в машинный/LLVM-код (и может настраивать параллелизм) — это **cold** (долго). Последующие вызовы с теми же типами используют готовый скомпилированный вариант — **warm** (быстро). В нашей работе cold serial ~0.54 s, warm ~1.15e-3 s (для контекста прогона) — разница в сотни раз.
3. **Когда `prange` даёт корректный результат, а когда приводит к гонкам? Почему при `prange` порядок суммирования может измениться?** Корректно, если итерации независимы и нет записи в одни и те же разделяемые переменные без синхронизации (или используются безопасные редукции). Гонки возникают при параллельной записи/чтении-modify-write в общую память без атомариков (например, общий счётчик/аккумулятор без reduction). Порядок суммирования меняется из‑за параллельного выполнения и разного разбиения по потокам (недетерминированный порядок объединения частичных результатов), что для float может давать немного разные округления, но при одинаковых входах и корректной схеме часто практически совпадает; в целых суммах по фиксированному набору значений результат одинаков.
4. **Почему векторизация может увеличить потребление памяти? Приведите пример из варианта.** Создаются временные массивы для промежуточных результатов. Пример: `xs*xs + ys*ys <= 1.0` создаёт временные массивы квадратов (и/или промежуточные буферы) плюс булеву маску/аргументы для `count_nonzero`; для `exp(-us*us)` — массив `us*us`, затем `-...`, затем `exp(...)`. В отчёте traced-память NumPy ядра для больших `size` достигает ~146 MiB при суммарных входах порядка ~6.4e6 значений в разных массивах — заметный рост относительно “in-place”-стиля Numba.
5. **Что такое порог окупаемости N* и как его найти экспериментально?** Это размер задачи `N*`, при котором время/затраты ускоренного варианта (с учётом накладных расходов: компиляция, создание процессов, копирование данных) становятся не хуже baseline (или достигается целевой speedup). Экспериментально: прогнать измерения для ряда `N`, построить графики `T(N)` для подходов, найти пересечение кривых (или порог по `T_impl(N)+overhead ≤ T_base(N)`).
6. **Почему для численных задач NumPy и Numba обычно выигрывают у `ProcessPoolExecutor`? Когда процессы всё же оправданны?** Потому что вычисления идут в скомпилированном коде без огромных накладных расходов IPC и без дублирования интерпретаторской работы в том же виде; процессы добавляют стоимость запуска, сериализации и копирования данных. Процессы оправданны при очень тяжёлых независимых задачах, разнородных заданиях, необходимости изоляции, или когда данные/вычисления естественно распределены и объём полезной работы велик относительно передачи (или передача не нужна, как в e2e с генерацией на месте — но в нашей реализации всё равно был проигрыш на малых/средних размерах из‑за оверхеда).
7. **Зачем в тестах задавать `atol` от масштаба данных? В каких случаях результат нужно сравнивать строго?** Из‑за ошибок округления float результаты разных порядков вычислений могут различаться на малую величину; `atol` защищает от ложных срабатываний при значениях около нуля/малых масштабах. Строгое сравнение (`==`) нужно для целых/deterministic-логики без float, для идентичности байтов/структур, или когда спецификация требует битовой точности (но обычно для float — `allclose`).
8. **Что изменит `fastmath=True` и почему это нужно проверять тестами?** Разрешает агрессивные оптимизации с плавающей точкой (перестановки/ассоциативность, упрощения `-ffast-math`), что может ускорить вычисления, но изменить результаты (порядок сумм, обработку NaN/Inf/знаков) и иногда нарушить требования к точности — поэтому обязательно проверять тестами на допустимость погрешности и корректность граничных случаев.
